# 商家端落地方案对比（待选）

> 目的：在不破坏现有用户端演示的前提下，把商家管理后台纳入同一仓库。
> 选定后：更新 [DECISIONS.md](../DECISIONS.md) 的 D-001，再按对应方案文档执行。

## 共同前提（四个方案一致）

1. **纯前端离线演示**：无后端，Mock 数据 + localStorage。
2. **手机优先**：375 设计稿、底部 TabBar、二级全屏页、安全区适配。
3. **用户端零回归**：5 个页面（选茶/制茶/商城/详情/购物车）行为不变。
4. **商家端全部懒加载**：不进用户端首屏，主包体积不变。
5. **数据不双写**：`catalog` 只读源 + 覆盖层（见 [merchant-app.md](../architecture/merchant-app.md) 4.5）。
6. **共享 Oil UI 与设计令牌**：不引入第三方 UI 库（见 D-002）。

## 一张表

| 维度 | A 路由分区 | B 顶层分区 | C monorepo | D 多入口 |
|---|---|---|---|---|
| 一句话 | 单应用加一棵路由树 | 单应用按 app 物理分区 | 工作区拆两个应用 | 同仓库两个 HTML 入口 |
| 目录 | 现有 `src/` + `src/merchant/` | `src/apps/{user,merchant}` + `src/shared` | `apps/*` + `packages/*` | `src/{user,merchant,shared}` + 2 入口 |
| 构建次数 | 1 | 1 | 2（可并行） | 1–2（按入口） |
| 产物 / APK | 1 / 1 个 APK 双身份 | 1 / 1 个 APK | 2 / 2 个 APK | 2 入口 / 可 2 个 APK |
| 一次性迁移量 | 小（预留目录已建好） | 中（约 45 文件、120 处 import） | 大（全仓重构 + CI） | 中（B 的迁移 + 入口配置） |
| 工期（不含功能） | **0.5 天** | 1.5 天 | 3.5–4 天 | 2 天 |
| 优点 | 最快、风险最低、零新依赖 | 边界清晰、可平滑进化 | 隔离最好、可独立发版招人 | 两端体积彻底分开、可分别部署 |
| 代价 | 边界靠约定、后期要再搬 | 仍是单一构建、商家端在用户端包内 | 工程最复杂、壳/字体/CI 双份维护 | 共享层必须提前抽干净、两个入口壳 |
| 适合 | 演示期、单人维护 | 长期单 APK 双角色 | 要拆产品线、多团队 | 商家端要独立 H5 或 APK |

## 推荐路径

1. **现在选 A**：0.5 天落骨架，再按开发文档 8.5 人日完成 P0 → 演示可用。
2. 当商家端页面超过 10 个，或需要给运营一个独立包时，再迁 **B**（约 1 天）或直接 **C**。
3. **不建议一步到 C**：需求还没验证就先付工程成本，对演示项目不划算。

迁移成本参考（代码写法已按可迁移约束）：A→B ≈ 1 天，B→C ≈ 1.5 天，A→D ≈ 1.5 天。

## 选定后怎么做

1. 在 `DECISIONS.md` 的 D-001 打勾，写结论与日期。
2. 按 `01`~`04` 对应文档执行迁移。
3. 交付标准：`npm run typecheck`、`npm run build` 通过 + 用户端 5 页回归 + 商家端登录页可达。
